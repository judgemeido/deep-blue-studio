# DEEP BLUE · 一步棋背后的机器

版本：方案 v1.0 · 2026-10-16

状态：供监督审阅；实施以本方案定稿后的分阶段任务为准。

使用技能：three-product-studio。

建议项目位置：`C:\Codex\city\deep-blue-studio`，单独使用 Git 管理。当前交付物为方案文档。

## 1. 项目要让观众带走什么

核心展签建议：

> 深蓝的力量，来自人设计的棋类知识、搜索算法，以及让这些计算高速运行的并行机器。

深蓝比赛时的核心决策是搜索与局面评估，结合专用象棋芯片和并行服务器；它不以现代深度神经网络作为落子引擎。表述也要保留边界：团队使用了棋谱资料与赛前辅助调参方法，因此不把“没有现代深度学习引擎”扩大成“完全不用数据或学习方法”。[S1、S2、S3]

观众完成体验后，应能用自己的话回答：

1. 为什么外表像两个大柜子的东西，实际是一套协同计算系统？
2. 为什么算棋需要搜索，但又不能把所有变化都算完？
3. 为什么剪枝后可以少算一些分支，却保持这个教学搜索的结果？
4. 为什么专用芯片能把固定任务做得更快；它与通用处理器如何分工？
5. 1997 年的胜利由哪些工程与人的工作共同促成？

建议目标用户为没有计算机专业背景的观众。不要求先懂国际象棋记谱法；初次体验约 5–8 分钟，随时可以自由观察或回到上一步。这是体验目标，不是开发工期。

## 2. 在建模之前锁定的事实与表现边界

| 原始设想 / 易混点 | 本方案采用的处理 | 依据与审核条件 |
| --- | --- | --- |
| 30 个节点、480 颗芯片 | 以 1997 年比赛系统的作者论文为配置基线；界面标注“比赛搜索配置”。机柜槽位容量另据参考照片确认 | [S1]；IBM 简史及当年宣传材料也出现 32 节点口径，不能把不同口径混成一套实物配置 |
| 每个节点两颗主 CPU | 节点重点展示一个 P2SC 处理器；主处理器也执行上层搜索，并负责分派工作 | [S1]，不将 CPU 只表现为发任务的交换机 |
| 一张板上 16 颗象棋芯片 | 每节点两块 Micro Channel 加速卡，每卡 8 颗，总计 16 颗 | [S2]；模型数量必须与资料清单一致 |
| 芯片内三个区域包括置换表 | 采用四个教学功能区域：着法生成、局面评估、搜索控制、走法栈与重复检测。置换表在软件搜索层说明 | [S1、S2]；彩色区域是功能示意，不声称为真实版图分区 |
| 一个周期完成一步棋推理 | 说明硬件执行专用子任务；快速评估与完整搜索的耗时不同，不能混为一个时钟周期 | [S2]；不展示虚构的整步棋单周期动画 |
| 每秒 2 亿“步棋” | 面向公众使用“约每秒 2 亿个局面”的常用指标，并在展开资料中注明局面与搜索条件会影响速度 | [S1、S4]；展示指标不当作浏览器运行测速 |
| 第二局的远见着法就是随机 Bug | 第一局的随机落子故障与第二局的争议着法分别叙述。Bug 对心理或胜负的影响标为推测 | 团队成员 Campbell 的直接访谈 [S5] |
| 第六局结束 | 采用“1997 年 5 月 11 日，第六局 19 回合后卡斯帕罗夫认输；总比分 3.5∶2.5” | [S4、S6]；不以“精神崩溃”代替可核验比赛结果 |
| 黑柜、蓝带、铭牌、灯窗 | 以 1997 年照片确认轮廓、柜门和标识位置；蓝色优先用于界面与重点照明，装饰带须有实物依据 | [S7]；首轮审核前建立正面、侧面、开门参考板 |
| QFP 陶瓷封装、指定芯片编号 | 封装与丝印须由近摄资料确认；暂定尺寸与内部结构均带“教学重建”说明 | 已有裸片照片 [S8]；不能从裸片照片反推封装细节 |
| 机柜前的棋桌、空椅和倒笔 | 作为展览式空间编排；在场景说明注明“机房与比赛元素的叙事组合” | 棋桌与机柜的相对摆位不作为现场复原证据；倒笔先不列入必做资产 |
| DGT 品牌、1.4 吨、机柜精确尺寸、人脑 20W | 放入待核资料清单，确认来源及统计口径后才进入展签；先以比例示意建模 | 不将估计数字包装成实测，不计算缺乏同口径的能耗倍率 |
| 香农数 10^120 | 如使用，明确为对棋局变化规模的估计，不称“合法局面总数” | 数值出处补齐后进入扩展说明；不列首屏大数字 |
| ASIC 是现代 AI 芯片的直系祖先、唯一出路 | 结尾讲“面向任务的硬件设计”这一共同工程思想；不建立未经论证的直接谱系或唯一道路 | 作为工程启发与比较，不作为历史因果结论 |

资料处理采用三类标签：**史料确认 / 教学示意 / 待核实**。对外主展签优先使用前两类，并在展开说明中给出来源。争议口述与确定日期分开呈现。

## 3. 一个展台，三层深度

采用同一个可旋转的 3D 场景，配合“集群 → 节点 → 芯片”面包屑。点击部件和点击对应 DOM 按钮走同一条操作路径。屏幕上始终保留当前层级、当前问题和回到上一层的入口。

| 层级 | 场景与镜头 | 本层唯一核心问题 | 观众动作 | 完成后应看到的反馈 |
| --- | --- | --- | --- | --- |
| 宏观：集群 | 双机柜与棋桌构成主体；镜头先停在可读的三分之四正面 | “一个棋局，为什么需要这么大的机器？” | 点击“追踪这一着棋”，再选择示范节点 | 棋盘局面进入系统，节点被依次标记；讲清“一套协作系统” |
| 中观：节点 | 开门 → 镜头移向目标节点 → 节点沿抽出方向离柜；CPU、两张加速卡与通信连接可辨认 | “它怎样少算一些，又同时算很多？” | 开关剪枝，逐步展开同一棵小型博弈树；切换任务分发视图 | 最终分值一致，访问节点数改变；任务从软件层送往芯片层 |
| 微观：芯片 | 一块 8 芯片板卡抬出 → 聚焦其中一颗 → 封装与裸片教学分层 | “哪些计算被做进了电路？” | 分别点亮着法生成、评估、搜索控制、重复检测 | 小棋盘、功能区与解释同步；看见每一步的输入与输出 |

第 14 号节点可作为教学选中节点；编号仅用于导航，不赋予它未经证实的特殊历史角色。

历史旁线随层级出现：宏观放比赛时间轴；中观放 ChipTest / Deep Thought 到 IBM 团队的演进；微观放专用计算的设计取舍。每层先讲清问题，再允许展开人物与史料。

## 4. 让第一次来的观众能跟着做

默认提供引导模式，入口文案为：**“用 5 步看懂深蓝如何算一着棋”**。自由探索与重新开始始终可达。

| 步骤 | 直接呈现给观众的提示 | 允许的操作与教学结论 |
| --- | --- | --- |
| 1. 接到一个问题 | “棋盘上出现了一个新局面。机器要比较自己和对手接下来可能怎么走。” | 点击“开始比较”；显示当前局面与少量候选分支 |
| 2. 看见搜索树 | “每往下一层，就是一方走一次。我们希望自己的选择好，也假定对手会作出有利于它的回应。” | 逐步展开 2–3 层小树；先懂双方交替选择，再展开 Minimax 术语 |
| 3. 亲手减少计算 | “打开剪枝，看看哪些分支已经不会改变当前选择。” | 同一棵树与相同遍历顺序对比；显示访问计数、保留的结果和剪枝原因 |
| 4. 分给多台机器 | “上层搜索产生的任务被分发给工作节点，节点再把任务交给专用芯片。” | 高亮一条任务路径；打开节点与板卡，避免用纯粒子流代替任务含义 |
| 5. 看懂专用芯片 | “芯片生成着法、评估局面、控制搜索，并检查重复。主机汇总这些工作继续作出选择。” | 点亮四个功能区；回到整机，展示本次教学搜索的选择与理由 |

每步提示固定包含：**现在做什么 / 看哪里 / 这说明什么**。完成条件由真实操作和计算状态触发；暂停、重播与直接看结果不会偷偷推进另一套状态。所有动画可暂停、回退，重播使用同一份结果。

入门先解释“对手也会反击”，再引出 Minimax；先看到“结果不变、少访问了节点”，再解释 Alpha-Beta。每层只出现一个主要行动按钮，初始可见热点最多 3 个。

## 5. 算法实验与历史回放分清来源

### 5.1 真正可执行的原理实验

- 固定的一组小型数值博弈树，同时提供完整 Minimax 与 Alpha-Beta。两者使用相同叶子分值、深度与排序，验证返回值一致，显示实际访问节点数。
- 每个剪枝节点可点击查看原因，例如：“这个分支已不可能改善祖先节点的当前选择”。高级展开才显示 α、β 和上下界。
- 开关只改变计算策略，不换题目、不换评分。调整着法排序时明确展示顺序变化；避免暗示剪枝比例固定。
- 并行教学展示同一批任务在 1、4、8 个虚拟工作节点之间分配；界面明确为调度示意。若显示浏览器实测时间，单独标明设备、任务与测量范围。
- “30 个搜索节点、480 颗芯片”是历史配置标签；浏览器演示的节点数、动画速度和访问次数是教学数据，分别标注。

### 5.2 1997 年历史回放

选择少量经核对的棋谱片段，包含第二局的争议着法与第六局结尾。提供上一着、下一着、坐标与简短解释；默认用“白方象移到 e4”等自然语言，记谱法按需展开。

回放棋谱与本次教学算法是两个数据来源。未经历史日志支持的动画标注“原理演示”，不声称重建当时完整搜索路径、估值或耗时。

历史重点先使用比赛结果、工程团队与系统迭代。随机 Bug 的口述放在“误读机器”的附加展签中，同时显示第一局与第二局的区别，保留心理影响的不确定性。[S4、S5、S6]

## 6. 视觉方向与模型资产

方向：**1997 年工业计算档案馆**。机柜为主角，历史道具服务理解，文字和交互入口具有清楚边界。

| 对象 | 必做表现 | 本轮建模依据 / 表现边界 |
| --- | --- | --- |
| 双机柜 | 硬朗轮廓、真实倒角、喷塑钢板、柜门网孔、铰链、底座、克制灯光 | 照片为外观基准；网孔优先材质表现，避免海量独立孔洞 |
| 棋桌与终端 | 木质棋盘、少量棋子、CRT 外形与可读终端摘要 | 棋谱可核验；终端内容如无原始截图则标明示意 |
| 节点 | 可抽出的外壳、CPU 散热器、两块独立加速卡、后端连接 | 内部不遮挡关键拓扑；滑轨与线束若为合理重建则说明 |
| 加速卡 | 每卡 8 芯片、连接器、阻容器件、适量走线 | 同一节点 2 卡；板形与器件排布待照片补齐后锁定 |
| 芯片 | 封装、引脚、裸片表面、四个可交互功能区 | 功能区为教学覆盖层；裸片特征参考 [S8] |

建议色彩：背景深灰蓝 `#111923`，工业柜体炭黑 `#20252A`；主信息区用暖纸色 `#ECE7DC`，正文深墨色。蓝色 `#3D7CDA` 表示当前层级与选中对象；琥珀色 `#D7A14A` 表示当前正在执行的任务。颜色同时配合文字、轮廓和编号，不只靠色差表达状态。

重要区域的外边框使用明确的深色实线；当前操作对象加双层轮廓或外圈。普通说明使用较弱分隔线，防止所有东西同样抢眼。选中态保持稳定，不用持续闪烁吸引注意。

灯光采用大面积主光、侧向轮廓光和克制环境反射；黑色机柜的边缘与门缝必须可读。历史厚重感来自材料、比例、档案编号、日期和真实出处，不依赖昏暗、重颗粒或泛光。

## 7. 拆解动作与页面编排

### 拆解顺序

柜门开启并让出通道 → 节点沿滑出轴完整离柜 → 外盖独立移开 → 板卡解除连接后沿安装方向取出 → 聚焦芯片并展开教学剖面。

每个动作具有起始姿态、局部转轴、终点与运动包围盒。先用低精度模型确认间距；相机、部件和标注由一个步骤进度同步。线缆在抽出前显示脱开状态；连接器不会在仍连接时被强行拉长。提供一键复原，复原从原始姿态计算，反复拆合不积累偏移。

微观阶段明确显示“放大示意”和回到原比例的入口。真实尺寸只在资料充分时标注；没有实测依据时保持一致的展示单位。

### 默认一屏

桌面：顶部为标题与三层面包屑；中央约 2/3 空间展示模型，其余为当前问题、步骤和反馈；底部紧凑显示步骤导航与暂停/复原。历史文章与完整资料点击展开。

手机：模型与当前动作提示优先，步骤收敛成一张当前卡片，来源与历史使用可关闭抽屉。画面构图随剩余空间适配，不把桌面界面等比缩小。

初始验收视口建议为 1366×768、1440×900、1280×720、1024×768，以及 390×844、360×800。核心实验和当前指引须同时可达；极矮横屏窗口使用可滚动回退。打开抽屉时暂停演示，关闭后恢复焦点。

层间过渡先保持对象连续，再移动镜头；默认约 0.8–1.4 秒，最终以实测可读性调整。仅在确有资源准备时显示加载进度，按加载、解码、建模、材质预热等已完成工作更新，不用虚假计时百分比。减少动态效果时直接到达相同结果。

## 8. 实施结构

建议沿用现有项目的 JavaScript、Three.js 与 esbuild 方式，新建独立项目。长方体工业结构优先程序化建模；确实需要复杂雕刻或外部实物模型时才引入 GLB。

| 模块 | 负责的内容 | 关键约束 |
| --- | --- | --- |
| `dimensions` / `reference-manifest` | 尺寸、单位、轴向、来源与可信度 | 同一份数据驱动几何、运动和展签 |
| `models` | 机柜、节点、板卡、芯片及可拾取部件 | 不持有教学文案或 DOM 状态 |
| `journey-state` / `commands` | 层级、选中对象、拆解进度、引导步骤、暂停和复原 | 按钮、热点、键盘共用命令 |
| `teaching-search` | 小树、Minimax、Alpha-Beta、访问记录与剪枝理由 | 纯算法；教学数值可复现 |
| `history` | 比赛日期、棋谱片段、口述与参考索引 | 历史回放与教学计算分开标记 |
| `ui` / `annotations` | 当前指引、重点边框、部件说明、来源抽屉 | 原生控件可用；投影标注与模型同步 |
| `rendering` | 相机、灯光、材质、按需加载与释放 | 移动质量降级；切换阶段不重复创建全套场景 |

重复芯片、螺丝等使用实例或同材质批次；只在同一运动组内合并几何，保留可拆部件边界。材质渐隐使用明确持有的实例，场景切换释放不再使用的资源。

必要技能是已指定的 three-product-studio。浏览器验收沿用环境允许的工具；只有引入复杂 GLB 时再使用资产管线技能，保持依赖与任务相称。

| P3 · 可执行教学 | 小型博弈树、剪枝比较、任务分配、完整五步指引 | 能否看懂每次操作与结果，数据是否真实对应 | 相同树返回值一致；计数来自实际运行；每步明确告诉看哪里 |

| P5 · 完整验收 | 转场、加载、历史回放、响应式、性能与回归报告 | 首屏、连续操作、设备适配、史料与模型一致性 | 验收表完成，已知边界写明，构建和功能/视觉证据齐全 |

P1 优先完成可运行轮廓与运动关系，昂贵纹理、线缆细节和精细道具安排在结构确认以后。初步工期在 P0 参考资料齐全、P1 复杂度明确后估计；当前不把未知资料和建模工作压成不可靠的天数承诺。

## 10. 最终验收与可观察指标

| 维度 | 检查方式 | 通过条件 |
| --- | --- | --- |
| 初见可理解 | 只看首屏，说明正在研究什么以及从哪里开始 | 目的、当前步骤与唯一主按钮清楚可见 |
| 教学闭环 | 从开始到芯片再回整机逐步操作 | 每步都有操作、观察和结论；中断后能继续或重来 |
| 史实 | 对照来源索引复核每个主要展签 | CPU、板卡、芯片、日期与争议说明统一口径 |
| 算法 | 比较完整搜索与剪枝的实际输出与访问日志 | 相同输入返回值相同；剪枝解释符合界限条件 |
| 几何与运动 | 检查关闭、半开、全开及正/侧/俯视 | 柜门、抽屉、板卡和相机没有遮挡关键动作或穿插 |
| 信息重点 | 查看默认、当前操作、运行完成、弹层四种状态 | 当前对象及主要操作边框明确；正文可读；热点不堆叠 |
| 响应式与可访问 | 指定视口、键盘操作、减少动态效果、极矮窗口 | 核心操作可达；弹层可关闭；焦点与阅读顺序合理 |
| 生命周期 | 重复进入/退出三层、重播和复位 | 状态不串位；资源计数无持续单向增长；无重复渲染循环 |
| 加载与失败 | 冷启动、资源失败、重试、快速切换 | 进度对应实际阶段；错误可解释、可恢复 |
| 性能 | 指定设备记录帧时与场景统计 | 暂定桌面目标 60 fps、手机目标 30 fps；P1 后锁定参考设备和质量档位，以实测报告为准 |

低风险文案与视觉调整用浏览器验收，不堆叠只检查实现拼写的测试。算法正确性、拆解关系与状态恢复采用有实际意义的测试。每次验收保留截图、操作步骤、构建结果与设备范围。
